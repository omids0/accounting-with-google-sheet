# UX Round 11 — Implementation Spec (building manager: one workspace per building)

Audience: the Claude agent that will implement this. The owner approved the direction over the six `round11-flow-*.html` wireframes (a 24-screen walkthrough); details marked **ask first** need the owner's answer before that step starts. Everything else is decided.

Rounds 1–9 precede this and must be **merged** first. Round 10 is **not** required. Wireframes: `round11-flow-1.html` (screens 1–4: personal drawer, empty home, the two-step building form), `round11-flow-2.html` (5–8: quick unit builder, home card, calm building dashboard, building drawer), `round11-flow-3.html` (9–12: units, residents, charges, expenses lists), `round11-flow-4.html` (13–16: fund, building debts, checks, counterparties), `round11-flow-5.html` (17–20: unit page, unit form with people, issue sheet, payment and receipt), `round11-flow-6.html` (21–24: full expense form, building bank SMS, reports and مجمع, building settings and exit). Index: `index.html`.

The spec is written step by step with exact names on purpose. Follow the steps in order; each step ends with a check and a commit.

**Source of truth for look and behavior:** `round11-prototype.html` (one clickable file, app tokens, light + dark). Where a flow wireframe disagrees with the prototype (bottom nav, segmented chips for data values), the prototype and this spec win.

## Decisions after review (override anything below that disagrees)

1. **No bottom nav in a building workspace.** Everything lives in the drawer. `Layout.tsx` renders no `LayoutBottomNav` when the workspace type is `building`; the speed dial (FAB) stays per page. There is no `BUILDING_PRIMARY_NAV_TABS`.
2. **No segmented chips for data values.** Every choice that is stored (role, charge method, vacancy rule, expense kind, payer, split mode, issue day, due day, floor filter) uses the app's `Select` / `FormSelect` (or `PickerSheet` when the list is long), with options from the registry in Decision 3. Segments remain only for view switches (unit page: صورت‌حساب | سابقه | ساکنان | مشخصات) and filter chips, as elsewhere in the app. A yes/no choice is a `ToggleSwitch`.
3. **Option registry, managed and extensible.** `src/components/buildings/buildingOptions.ts` exports typed lists `{ value, label, hint?, rule? }`: `RESIDENT_ROLES` (owner, tenant), `CHARGE_METHODS` (fixed, area, people), `VACANCY_RULES` (full, half, zero), `SPLIT_MODES` (equal, area, people, manual) — code-defined, logic keys fixed, labels in one place. Two lists are **user-managed per workspace**: `EXPENSE_KINDS` (defaults جاری → resident, عمرانی → owner; each kind carries `chargeTo: 'resident' | 'owner'`, so `shareDebtor` reads the rule from the kind, nothing hard-coded) and `EXPENSE_PAYERS` (صندوق, مدیر, plus any board member the manager adds; a payer other than صندوق creates the dang). Managed lists are stored as JSON rows `فهرست:<id>` in «تنظیمات دوره» (value `[{ value, label, chargeTo?, hidden? }]`), edited in building settings → «فهرست‌ها» with the same add / rename / hide / reorder pattern as the categories page; a kind or payer in use can be hidden, never deleted. New code-defined lists follow the same file and shape.
4. **Credit, not loss, on overpayment.** When a payment exceeds all open receivables of a unit, the sheet says «X بیشتر از بدهی است» and defaults to saving it as unit **credit**: an income record (category «شارژ ساختمان», `مرجع` = `credit:<unitId>`). `unitBalance` returns `credit`. Issuing a charge applies available credit first through `addReceivablePayment(..., { fromCredit: true })`, which closes the receivable without creating a second income record. The user can lower the amount instead.
5. **Debtor by id.** Receivables get two new last columns: `مرجع` (as in the Model table) and `شناسهٔ بدهکار` (counterparty id). Display and statements resolve the name from the id; the counterparty rename flow also rewrites the `debtor` text so older views stay right.
6. **Concurrent issue is safe.** Automatic issue runs only for the sheet's manager role (round-8 role «مدیر»); members see the dashboard card and may issue by hand. Both paths re-run `planIssue` against freshly synced receivables immediately before writing, and after every sync `dedupeChargeReferences` keeps the earliest receivable per `مرجع` and removes later **unpaid** duplicates with an activity entry «صدور تکراری حذف شد». A device writes `آخرین صدور = <YYYY-MM>@<deviceId>` in «تنظیمات دوره» first and aborts if another device's marker for that month is newer than 2 minutes.
7. **Version follows the app.** Do not hard-code 2.7.0. At the final step read `package.json` on `main`, bump the minor by one, and put that number in About and the changelog.
8. **Reimbursement is a transfer, not a second expense.** The pocket expense (payer «مدیر») is the one real expense and counts in reports when recorded. Settling the dang from the fund writes a wallet outflow in the system category «انتقال» (subcategory «بازپرداخت به مدیر»), which reports and «وصول − هزینه» skip like every other transfer; the fund balance drops by the amount.
9. **Ask-first item closed:** amount-only SMS matches never auto-confirm (the unit picker stays required).
10. **Quick units builder has three steps** (`QuickUnitsBuilderSheet.tsx`): (1) total units, total floors, reference area; (2) assign unit ranges floor by floor — each floor has a «تا واحد…» `Select`, and changing one floor redistributes the remaining units over the later floors, the last floor always ends at the total; (3) one area field per unit, all prefilled with the reference area, edited only for special units. Created owners are placeholders (`placeholder: true` on the counterparty).
11. **Unit completion flow** (`CompleteUnitsSheet.tsx`) opens right after the builder and from a guide card on the units page and dashboard while any unit still has a placeholder owner: one unit at a time with a progress bar — owner name, phone, card digits; occupancy `Select` (`OCCUPANCY`: مالک ساکن، مستأجر دارد، خالی) with tenant name and phone when needed; area, people, parking, storage, special charge. Actions: ذخیره و بعدی، رد کردن، قبلی. Saving writes the counterparty, the unit and the stay rows (closing the previous stay). Phone and card fields are text inputs, never number-formatted (leading zeros kept).
13. **Roles and permissions** (`src/services/buildingRoles.ts`, registry `BUILDING_ROLES` in `buildingOptions.ts`): every user of a building spreadsheet has one role, stored by e-mail as «تنظیمات دوره» rows `نقش:<email>`; the creator is «مدیر», the manager assigns the others in building settings → «اعضا». A connected sheet (`ConnectBuildingSheet`) takes the role from that row, default «عضو هیئت مدیره».

    | Permission | مدیر | حسابدار | عضو هیئت مدیره |
    |---|---|---|---|
    | `record`: payments, expenses, income, checks, bank SMS, dang settlement | ✓ | ✓ | — |
    | `issue`: manual charge issue | ✓ | ✓ | — |
    | `autoIssue`: automatic monthly issue | ✓ | — | — |
    | `people`: units, residents, counterparties, quick builder, completion flow | ✓ | ✓ | — |
    | `settings`: profile, lists, members and roles, remove connection | ✓ | — | — |
    | read: dashboard, units, residents, charges, expenses, fund, debts, checks, reports, statements | ✓ | ✓ | ✓ |

    `can(permission)` hides the controls and floating buttons a role cannot use, removes the drawer rows «پیامک بانکی» and «تنظیمات ساختمان» for roles without them, shows «دسترسی ندارید» on direct route access, and every gated action re-checks before writing. This is interface enforcement only: the real data access is the Drive share (مدیر and حسابدار = editor, عضو هیئت مدیره = viewer), so a viewer cannot write even if the check were bypassed. The wizard no longer asks for the creator's role. Prototype: role switcher in the side panel.
14. **No dead ends: a guided setup journey** (`BuildingSetupCard.tsx`, `buildingSetup.ts`, `nextSetupStep(building)`). Every screen that finishes a step offers the next one instead of dropping the user on a list. Steps in order: (1) units and floors (quick builder) (2) owner and residents of every unit (completion flow) (3) current balance of each fund account — also asked in the create form, so usually already done (4) previous debts of units, optional (5) first charge issue (6) invite the board and the accountant, optional. The dashboard shows a checklist card with progress and one primary «ادامه» button until every step is done or skipped (manager only). Completion of step 2 opens a summary («۱۲ واحد ثبت شد · مالک ساکن / مستأجر / خالی») with the next step as the primary button; saving or skipping a step opens the next step's sheet; finishing the last step goes to the dashboard. The first issue is always manual with a preview; only after a charge month exists does the monthly automatic issue (Decision 12) run, and never while any unit still has a placeholder owner. An empty charges page shows «صدور اولین شارژ». Connecting an existing sheet enters it straight away. Previous debts become receivables `بدهی قبلی` with `مرجع` `opening:<unitId>`; invites add the member with the chosen role and copy a ready invitation text.
15. **One guided journey, ending in a summary** (replaces the loose checklist as the main path; the checklist card stays as the fallback when the user leaves midway). «+ ساختمان جدید» runs one continuous flow with a persistent 8-step bar («قدم N از ۸»): مشخصات · صندوق و شارژ · واحدها · مالک و ساکنان · بدهی قبلی · شارژ اول · دعوت اعضا · جمع‌بندی. The building sheet is created at the end of step 2 and the flag `journey` stays on until the summary is confirmed. Every step opens the next one when saved or skipped, has «قبلی» from step 5 on, and the last screen («جمع‌بندی راه‌اندازی») lists the building, units and occupancy, accounts and total balance, charge settings, first issued month, previous debts, members and roles, explains what happens next, offers «اشتراک خلاصه» (copy) and «رفتن به داشبورد». Code: `buildingJourney.ts` (`JOURNEY_STEPS`, `goNextStep`), `JourneyStepper.tsx`, `JourneySummarySheet.tsx`.
16. **Dial pad for every money field** (`AmountKeypad.tsx`, `AmountField.tsx` wrapping the existing `AmountInput`): a money field is a button showing the formatted amount; tapping opens a bottom keypad (LTR digit grid 1–9, ۰۰۰, ۰, ⌫), a large live display, quick adds (+۱۰۰٬۰۰۰ / +۱٬۰۰۰٬۰۰۰ / +۱۰٬۰۰۰٬۰۰۰), «پاک کردن» and «تأیید»; the hardware keyboard also works. Used for expense, payment, income, check, opening balances, previous debts, default and per-unit charge, reconcile. Counts, areas, phones and cards stay plain inputs (phones and cards are text, never number-formatted).
17. **Defaults are always prefilled.** The monthly charge field of a unit (unit form and completion flow) opens with the building default computed by the charge method (`baseChargeFor`), not empty. If the user does not change it, the unit keeps following the method (`charge = 0`, so later changes of the default or the area apply); if changed, it becomes a per-unit override.
18. **Fund balance is changed by reconcile, never by editing the number.** Fund page → tap an account → «تطبیق موجودی با بانک»: the user enters the real balance on the dial pad, the sheet shows the difference, and saving writes one record of the new type `correction` (signed amount, category «اصلاح موجودی»); no earlier record changes, and corrections are skipped by reports and «وصول − هزینه» like transfers. «ویرایش حساب» changes name and card only (settings permission); «+ حساب جدید» takes an opening balance. This reuses the round-7 wallet reconcile flow.
19. **Members and permissions page** (`BuildingMembersPage.tsx`, route `building-members`, settings permission): each member card shows role, status (فعال / دعوت‌شده), a role `Select`, «دسترسی‌های دقیق» with one switch per permission (a changed switch marks the member «سفارشی»; «بازگشت به پیش‌فرض نقش» clears it; changing the role also clears overrides), and «قطع دسترسی» with a confirmation. At least one manager must always remain; the manager cannot demote or remove themselves. A note appears when a viewer-role member is given write permissions (the Drive share must be editor too). Invites come from here, from settings and from the journey. Effective permission = member override, else role default (`memberCan`). The prototype's side panel switches «من کدام عضو هستم» so the manager's changes can be tested.
12. **Auto issue on a new month:** entering the building workspace on or after the issue day issues every missing month for the manager role (`dedupeChargeReferences` first, `planIssue` re-run, due date = the profile due day), once per building per day, with the toast «شارژ <month> خودکار برای N واحد صادر شد». Other roles keep the dashboard card and the manual sheet. The prototype adds a «رفتن به ماه بعد» simulation button.

## The one architectural decision (read first)

**Every building is its own spreadsheet («فضای کاری»).** The app already supports several spreadsheets (`settings.spreadsheets`, `setActiveSpreadsheet` in `src/services/settings.ts`, `activateSpreadsheet` in `src/services/spreadsheetSetup.ts`, every localStorage key per spreadsheet, backup / close-the-year / sharing / search per spreadsheet). A building spreadsheet uses the **same engine** (records with categories, subcategories, line items, attachments and counterparties; wallet accounts; receivables; dang; checks; recurring items; bank SMS; reports; activity log; conflicts) but a **different menu and dashboard**, selected by a workspace type marker. Nothing of the building ever touches the manager's personal spreadsheet: no shared counterparties, no fund money in the personal net-available, no building categories in personal reports, no building rows in the personal widget. Sharing a building with board members = Drive sharing of that one spreadsheet (round 8 writer/activity/conflicts apply as is).

Two deliberate **bridges** between a building and the manager's personal spreadsheet exist (Step 7); nothing else crosses.
