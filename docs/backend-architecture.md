# معماری بک‌اند «حساب کتاب»

وضعیت: پیش‌نویس معماری · تاریخ: ۱۷ آبان ۱۴۰۵ · هم‌گام با نسخهٔ ۲.۲۲.۰ اپ (develop تا PR شمارهٔ ۲۳۷، «اسکن فاکتور»، میان‌بر دوربین داشبورد، و وصل یک رکورد به چند بدهی یا طلب)

این سند فقط **معماری بک‌اند** است: هر بخش بگوید چه چیزی هست، کجا می‌نشیند و چرا. بر پایهٔ بررسی خط‌به‌خط کد فعلی (داده، همگام‌سازی، ساختمان، حساب مشترک، نظارت والدین، خودرو، پیامک بانکی، یادآور، پشتیبان، امنیت) نوشته شده تا هنگام پیاده‌سازی همه‌چیز مشخص باشد.

دو تصمیم محوری این سند، به خواستهٔ صاحب پروژه:

1. **ساختار داده همان ساختار فعلی است.** هر تب فعلی یک جدول می‌شود، با همان ستون‌ها، همان شناسه‌ها و همان معنی. به این ترتیب داده و پشتیبان‌های فعلی بدون دگرگونی روی بک‌اند می‌نشینند (بخش ۵).
2. **پشتیبان‌گیری فعلی روی Drive می‌ماند** و از آن بازیابی روی بک‌اند ممکن است. پایان راه: همه‌چیز روی بک‌اند خودمان، به‌علاوهٔ یک پشتیبان روی Drive که بشود از آن بازیابی کرد (بخش ۹).

دامنهٔ کار، ترتیب اجرا و تغییرهای لازم در کلاینت **عمداً در این سند نیستند**؛ فهرست آن‌ها در بخش ۲۰ برای گفتگوی بعدی آمده است.

**نگهداری این سند:** این سند با کد همگام می‌ماند. هر تغییر در تب‌ها و ستون‌ها، قالب پشتیبان، همگام‌سازی، ورود و دسترسی، قواعد دامنه یا وابستگی‌های بیرونی باید در همان کار اینجا هم بیاید، همراه با «درباره» و README. قاعدهٔ `keep-about-page-updated` در `.claude/rules/` و `.cursor/rules/` همین را الزام می‌کند. سطر نسخه و تاریخ بالای سند در هر به‌روزرسانی تازه می‌شود.

## ۲. هدف‌ها و اصل‌ها

هدف‌ها:

- اپ فعلی با همان تجربه (آفلاین‌فرست، فوری، فارسی) روی بک‌اند تازه کار کند.
- ورود فقط با شمارهٔ موبایل و رمز پیامکی.
- همهٔ زیرساخت داخل ایران.
- داده و پشتیبان‌های موجود، چه در Sheets و چه در zip، روی بک‌اند بنشینند و برعکس.
- دسترسی‌ها، یکتایی‌ها و تراکنش‌ها سمت سرور اجرا شوند، نه به رفتار کلاینت واگذار شوند.
- امکان درآمدزایی با اشتراک.

غیرهدف‌ها:

- بازنویسی گزارش‌ها روی سرور.
- انتقال کارهای روی-دستگاه به سرور: خواندن فاکتور با OCR و خواندن پیامک بانکی روی گوشی می‌مانند.
- رمزگذاری سرتاسری؛ یادآور، پیامک و اشتراک به داده در حالت خوانا نیاز دارند.
- ریزسرویس و Kubernetes.

اصل‌ها:

1. **ساختار فعلی منبع حقیقت است.** هر تغییر ساختار داده باید از رجیستری تب‌ها بگذرد، نه از کد پراکنده.
2. **آفلاین‌فرست حفظ شود.** کلاینت آینهٔ کامل را نگه می‌دارد و سرور منبع حقیقت است.
3. **یک موتور همگام‌سازی برای همهٔ جدول‌ها.** هیچ ماژولی همگام‌سازی جداگانه ندارد.
4. **داده همیشه قابل خروج باشد** با همان zip فعلی.
5. **هیچ وابستگی به سرویس خارج از ایران در مسیر درخواست.** تنها استثنا اتصال اختیاری کاربر به Drive برای پشتیبان است و آن هم از دستگاه خود کاربر انجام می‌شود.
6. **پول با عدد اعشاری شناور ذخیره نمی‌شود.** `numeric` و قاعدهٔ گردکردن فعلی (دو رقم، نیم به سمت دورتر از صفر).

## ۳. زبان و پشتهٔ فناوری

### پاسخ: TypeScript

دلیل‌های مشخص از همین پروژه:

- منطق دامنه امروز خالص و TypeScript است: شارژ ساختمان، تقسیم دنگ، پیش‌بینی نقدینگی، سود و زیان صندوقچه، موجودی ابتدای ماه، ادغام پرداخت‌ها، تراز حساب مشترک، وام. روی سرور بدون بازنویسی اجرا می‌شود.
- **تجزیه‌گرهای سخت‌گیر داده‌های قدیمی** (`parseSheetRecords`، `remapLegacyRow`، `normalizeSheetDate`، `parseNumeric`، `parseCreatedAtMs`) همین حالا نوشته و آزمایش شده‌اند. چون بازیابی از پشتیبان قدیمی ستون فقرات این معماری است، اجرای عین همین کد روی سرور مهم‌ترین مزیت است.
- تاریخ شمسی و نرمال‌سازی متن فارسی (`normalizeSearchText`، `normalizeDigits`) یک‌بار نوشته شده‌اند.
- قرارداد API با Zod یک‌بار تعریف می‌شود و برای کلاینت و سرور نوع و اعتبارسنجی می‌دهد.
- برای یک توسعه‌دهندهٔ تنها، یک زبان و یک زنجیرهٔ ابزار یعنی سرعت بیشتر.
- هزینهٔ این انتخاب: Node.js در بار همزمان بسیار بالا ضعیف‌تر از Go است. با حجم داده‌ای این اپ (هر کاربر چند هزار ردیف) این نقطه ضعف عملی نیست.

| گزینه | مزیت | چرا انتخاب نشد |
| --- | --- | --- |
| زبان Go | یک فایل اجرایی، مصرف کم | هیچ کد مشترکی با اپ ندارد؛ تجزیه‌گرها و منطق دامنه باید از صفر نوشته شوند |
| زبان PHP با Laravel | بیشترین نیروی بازار در ایران | همان مشکل کد مشترک |
| زبان Python با Django | پنل ادمین آماده | کد مشترک ندارد |
| چارچوب NestJS | ساختار اجباری | بار مفهومی زیاد برای تیم کوچک |

## ۴. معماری کلی

```
 اپ وب (PWA)          اپ اندروید (Capacitor)
      \                    /
       \  HTTPS / SSE     /          (اختیاری، از دستگاه کاربر)
        v                v          +----------------------------+
   +---------------------------+    | Google Drive کاربر         |
   |  CDN داخلی (فایل ثابت)     |<-->| پوشهٔ «پشتیبان» (zip)       |
   +---------------------------+    +----------------------------+
                 |                            ^
                 v                            | zip
   +---------------------------------------------------------+
   |  پروکسی (TLS)                         درگاه پیامک        |
   |    |                                  (OTP + اطلاع‌رسانی) |
   |  api (Fastify) ---- worker (BullMQ)         ^            |
   |    |   |   |            |   |               |            |
   |    |   |   +-- Redis ---+   +---------------+            |
   |    |   +------ فضای فایل (S3)       درگاه پرداخت         |
   |    +---------- PostgreSQL ---- پشتیبان سرور              |
   +---------------------------------------------------------+
```

مسئولیت‌ها:

- **سرویس api:** احراز هویت، مجوزها، همگام‌سازی، واردکردن و خروجی zip، فایل‌ها، اشتراک.
- **سرویس worker:** پیامک، یادآورها، صدور خودکار شارژ، عکس ماهانهٔ دارایی خالص، نرخ ارز و طلا، پشتیبان سرور، پاک‌سازی.
- **پایگاه PostgreSQL:** تنها منبع حقیقت.
- **حافظهٔ Redis:** کد OTP، شمارندهٔ نرخ، صف.
- **فضای Drive کاربر:** فقط مقصد اختیاری پشتیبان، با ارتباط مستقیم دستگاه کاربر.

## ۵. ساختار داده: همان ساختار فعلی

### ۵.۱ قاعده

- هر **تب** فعلی یک **جدول** است؛ هر **ستون** یک ستون. ترتیب ستون‌ها، عنوان فارسی ستون‌ها و معنی هر ستون همان است.
- **شناسه‌ها** همان UUIDهای تولیدشده در کلاینت‌اند. ایجاد ردیف idempotent و آفلاین‌پذیر می‌ماند.
- **ارجاع‌ها همان ارجاع‌های فعلی‌اند.** ارجاع با شناسه جایی که شناسه است (حساب، رکورد، گروه، خودرو) و ارجاع با نام جایی که نام است (دسته، طرف حساب در رکورد و چک و بدهی). تغییر این‌ها به ساختار بعدی واگذار می‌شود، نه این مرحله.
- **ستون‌های JSON داخل سلول همان‌طور می‌مانند** و به `jsonb` می‌روند: پرداخت‌های بدهی و طلب، وضعیت پرداخت اقساط، اقلام فاکتور، لوکیشن و تلفن و حساب‌های بانکی طرف حساب، الگوی پیامک، اقلام مکانیک، قبل و بعد در گزارش فعالیت. منطق ادغام بر اساس شناسهٔ پرداخت (`mergePaymentsById`) در سرور اجرا می‌شود.
- **برچسب‌های متنی که منطق را می‌رانند همان‌طور می‌مانند** («ثبت از پیامک»، «تکرار ماهانه»، پیشوند «چک: / قسط: / طلب: / بدهی: »، دسته‌های «چک، قسط، بدهی، تطبیق، اصلاح موجودی»، ستون «مرجع» با کلیدهای `charge:`، `share:`، `opening:`، `credit:`). کد فعلی روی آن‌ها اتکا دارد؛ سرور همان را اجرا می‌کند.
- ستون‌های مبهم داده‌های قدیمی (چند چیدمان برای بدهی، طلب و چک) فقط **در لحظهٔ واردکردن** با همان تجزیه‌گرها به چیدمان جاری تبدیل می‌شوند؛ جدول‌های سرور فقط چیدمان جاری را دارند.

### ۵.۲ رجیستری تب‌ها

یک فایل در بستهٔ مشترک (`packages/shared`) که برای هر تب مشخص می‌کند:

```ts
{
  tab: 'چک‌ها',                      // نام تب (برای پشتیبان و واردکردن)
  table: 'checks',                    // نام جدول
  workspaces: ['personal','building'], // در کدام نوع فضا وجود دارد
  key: ['id'],                         // کلید ردیف؛ برای تب‌های بی‌شناسه کلید طبیعی
  mergeKey: ['id'],                    // کلید ادغام در بازیابی «ادغام»
  columns: [
    { header: 'شناسه', key: 'id', type: 'id' },
    { header: 'زمان ثبت', key: 'created_at', type: 'ts' },
    { header: 'مبلغ', key: 'amount', type: 'money' },
    { header: 'پرداخت شده', key: 'paid', type: 'bool', emptyMeans: false },
    // ...
  ],
  aliases: { /* عنوان‌های قدیمی ستون‌ها */ }
}
```

این رجیستری **منبع واحد** است برای:

| مصرف‌کننده | چه می‌گیرد |
| --- | --- |
| ساخت جدول‌ها (DDL) | نام و نوع ستون‌ها، کلید |
| واردکردن (zip، CSV، آینهٔ Sheets) | نگاشت عنوان فارسی به ستون، نوع برای تجزیه |
| خروجی zip | ترتیب ستون‌ها و عنوان‌ها، قالب نمایش مقدار |
| مجوز | کدام تب در کدام نوع فضا مجاز است |
| همگام‌سازی | فهرست جدول‌های قابل همگام‌سازی و کلید ردیف |
| اعتبارسنجی API | طرح Zod ساخته‌شده از ستون‌ها |

رجیستری کامل همهٔ تب‌ها در پیوست الف است. معادل فعلی آن در کد: `sheetHeaders*.ts`، `sheetNames.ts`، `moduleSheetSpecs.ts` و فرم‌های `settings.ts`؛ رجیستری آن‌ها را یکجا جمع می‌کند.

| نوع در رجیستری | نوع PostgreSQL | واردکردن | خروجی |
| --- | --- | --- | --- |
| نوع `id` | `text` (یا `uuid` برای شناسه‌های UUID) | همان مقدار؛ شناسه‌های غیر UUID مثل `exp-…`، `bridge-…`، `legacy:…` را `text` نگه می‌دارد | همان مقدار |
| نوع `money` | `numeric(20,2)` | `parseNumeric` (ارقام فارسی و عربی، جداکنندهٔ هزارگان، منفیِ انتهایی، نویسه‌های نامرئی) | عدد ساده |
| نوع `qty` | `numeric(24,8)` | همان | عدد ساده |
| نوع `int` | `integer` | همان | عدد ساده |
| نوع `date` | `date` | `normalizeSheetDate` (ISO، شمارهٔ سریال Sheets، تاریخ شمسی، ارقام فارسی) | `YYYY-MM-DD` میلادی |
| نوع `ts` | `timestamptz` | `parseCreatedAtMs` (رشتهٔ `fa-IR`، `YYYY/MM/DD hh:mm`، ISO) با منطقهٔ `Asia/Tehran` | ISO |
| نوع `dt` | `timestamp` بدون منطقه | `YYYY-MM-DDTHH:mm:ss` محلی (تایم‌شیت) | همان |
| نوع `bool` | `boolean` | «بله / TRUE / true / 1 / yes» و مقدار پیش‌فرض خالی طبق `emptyMeans` هر ستون | «بله» و «خیر» |
| نوع `json` | `jsonb` | تجزیهٔ ایمن؛ ناخوانا یا غیرآرایه ← مقدار پیش‌فرض | JSON فشرده |
| نوع `text` | `text` | همان | همان |
| نوع `enum` | `text` | همان (برچسب‌های فارسی مثل «پرداختی» یا کلیدهای انگلیسی مثل `buy`) | همان |

نکته‌ها:

- **ستون‌هایی که باید متن بمانند:** شمارهٔ تلفن، کارت، شبا، حساب، شمارهٔ چک و صیادی، پلاک، VIN، شمارهٔ واحد؛ هر چیز با صفر اول یا بیش از ۱۵ رقم. هرگز به عدد تبدیل نمی‌شوند.
- **ماه شمسی** (`YYYY-MM`) در تب‌هایی که کلید ماه دارند همان `text` می‌ماند. برای گزارش‌های سرور ستون مشتق `jalali_ym` از تاریخ در برنامه محاسبه می‌شود.
- **ستون‌هایی با قالب ترکیبی** (مثل «زمان پرداخت» چک که گاهی تاریخ ISO و گاهی رشتهٔ فارسی است): به `ts` تبدیل می‌شود و متن اصلی در ستون سیستمی `legacy` می‌ماند.
- **ایمیل‌های درون داده** (ستون «ثبت‌کننده»، پرداخت‌کننده و ایجادکننده در حساب مشترک، `only:<email>` در تقسیم): همان متن می‌مانند. هنگام واردکردن، ایمیلی که با `users.legacy_email` برابر باشد به `user_id` نگاشت می‌شود؛ بقیه برچسب متنی می‌مانند.

### ۵.۴ ستون‌های سیستمی که اضافه می‌شوند

فقط افزودنی هستند؛ ستون‌های فعلی عوض نمی‌شوند.

```sql
workspace_id uuid not null,            -- بخشی از کلید اصلی
version      int  not null default 1,  -- تشخیص تعارض (If-Match)
last_seq     bigint not null,          -- شمارندهٔ همگام‌سازی فضا
created_by   uuid, updated_by uuid,    -- سرور مقدار می‌دهد، نه کلاینت
updated_at   timestamptz not null,
deleted_at   timestamptz,              -- حذف نرم برای همگام‌سازی آفلاین
legacy       jsonb                     -- متن اصلی سلول‌هایی که نرمال شده‌اند
```

کلید اصلی: `(workspace_id, id)`. برای تب‌های بی‌شناسه (دسته‌ها، بودجه، موجودی ماهانه، قاعده‌های یادآور و …) کلید طبیعی فعلی. ترتیب ردیف‌ها جایی که معنی دارد (دسته‌بندی‌ها) در ستون `position` ثبت می‌شود.

### ۵.۵ قیدها

داده‌های فعلی ناهمگن‌اند: شناسهٔ آویزان، شناسهٔ تکراری، ردیف ناقص. بنابراین:

- **کلید خارجی سخت وجود ندارد**، چون بازیابی یک پشتیبان قدیمی را می‌شکند. ارجاع‌ها «نرم»‌اند و خواندن‌ها مثل کد فعلی با شناسهٔ ناموجود کنار می‌آیند.
- **یکتایی‌هایی که از ستون‌های موجود به‌دست می‌آیند** اعمال می‌شوند:

| قید | روی چه |
| --- | --- |
| شارژ ماهانه، بدهی قبلی، سهم هزینه | ایندکس یکتای جزئی روی ستون «مرجع» در `receivables`، برای مقدارهای `charge:`، `opening:` و `share:` |
| ثبت پیامک | ایندکس یکتای جزئی روی `origin_ref` (بخش ۱۲) |
| شمارهٔ واحد فعال | یکتا در هر ساختمان |
| اقامت باز | حداکثر یک اقامت باز برای هر `(واحد, نقش)` |
| شناسهٔ تکراری | `PK (workspace_id, id)`؛ در واردکردن، اولین شناسه برنده است |

- **منطق قیود دامنه** (بخش ۱۰) در سرویس‌ها اجرا می‌شود، با تراکنش.

### ۵.۶ آنچه عمداً با ساختار فعلی فرق دارد

این‌ها مجبوریِ حذف Google هستند، نه بازطراحی:

| تب یا مفهوم فعلی | در سرور | دلیل |
| --- | --- | --- |
| ردیف‌های `نقش:`، `دسترسی:`، `دعوت:`، `والد:`، `اعلان:` در «تنظیمات دوره» | جدول‌های `workspace_members`، `invitations`، `guardianships`، `change_notices` | دسترسی‌ها را قبلاً اشتراک Drive تعیین می‌کرد؛ حالا باید در DB باشد (بخش ۶) |
| بقیهٔ ردیف‌های «تنظیمات دوره» (`نوع فضا`، `تاریخ عضویت`، `ماه شروع محاسبه`، `رنگ تم …`، `فهرست:*`، `راه‌اندازی`، `آخرین صدور`) | همان جدول کلید و مقدار | بدون تغییر |
| «قفل_اپ» | وجود ندارد | هرگز از دستگاه خارج نمی‌شود (همین حالا هم از پشتیبان بیرون است) |
| تب‌های سالانه (`هزینه ۱۴۰۳`) | ردیف‌ها وارد جدول اصلی می‌شوند | بایگانی فقط به‌خاطر محدودیت Sheets بود |
| «فعالیت» (دو تاریخ آخرین باز کردن و عملیات) | یک ردیف برای هر کاربر در `user_activity` | تک‌ردیفی شخصی بود |
| «یادآوری»، «ناتیف»، «یادآوری_ثبت» | به‌ازای هر کاربر، نه هر فضا | شخصی بودند |
| دسته‌بندی‌ها | ستون `position` اضافه می‌شود | ترتیب ردیف معنی دارد |

### ۵.۷ نمونه

```sql
create table checks (

  counterparty text,                 -- نام، مثل فعلی
  amount numeric(20,2) not null default 0,
  issue_date date, due_date date,
  paid boolean not null default false,

  transaction_record_id text,

  -- ستون‌های سیستمی بخش ۵.۴
```

## ۶. فضای کاری و دسترسی به داده

### مدل

هر «فضای کاری» امروز یک فایل Google Sheets است (شخصی، ساختمان، حساب مشترک)؛ «فرزند» نمای فقط‌خواندنی روی دستگاه والد است. کنترل دسترسی واقعی اشتراک Drive بود و نقش‌ها فقط در رابط اعمال می‌شدند. در سرور:

```sql
create table users (
  id uuid primary key,
  phone text unique not null,            -- E.164
  name text,
  legacy_email text,                     -- فقط برای نگاشت داده‌های قدیمی
  created_at timestamptz not null default now()
);

create table workspaces (
  id uuid primary key,
  type text not null check (type in ('personal','building','shared')),
  name text not null,
  owner_user_id uuid not null references users(id),
  seq bigint not null default 0,         -- شمارندهٔ همگام‌سازی (بخش ۸)
  created_at timestamptz not null default now(),
  archived_at timestamptz
);

create table workspace_members (
  workspace_id uuid references workspaces(id),
  user_id uuid references users(id),
  role text not null,
  overrides jsonb not null default '{}',
  status text not null check (status in ('invited','active','removed')),
  invited_by uuid, invited_at timestamptz, joined_at timestamptz,
  primary key (workspace_id, user_id)
);

create table invitations (
  id uuid primary key, workspace_id uuid, phone text not null, role text not null,
  token_hash text not null, expires_at timestamptz not null, accepted_by uuid
);

create table guardianships (
  id uuid primary key, child_user_id uuid, parent_user_id uuid,
  status text check (status in ('requested','active','revoked')),
  scope text[] not null, consented_at timestamptz, revoked_at timestamptz, revoked_by uuid
);
```

- هر کاربر با ثبت‌نام یک فضای شخصی می‌گیرد.
- «والد و فرزند» نوع فضا نیست، پیوند است.
- دعوت با **شمارهٔ موبایل** است؛ مدعو با اولین ورود با همان شماره دعوت را می‌پذیرد.

### کدام تب در کدام فضا

از `PERSONAL_ONLY_SHEETS`، `SHARED_ACCOUNT_SHEETS` و `CHILD_VIEW_SHEETS` فعلی؛ در رجیستری اجرا می‌شود.

| گروه تب‌ها | شخصی | ساختمان | مشترک | نمای فرزند برای والد |
| --- | --- | --- | --- | --- |
| درآمد و هزینه، دسته‌بندی‌ها، بودجه، تنظیمات دوره، گزارش فعالیت | بله | بله | بله | خواندنی (دسته‌ها، بودجه، دوره، رکوردها) |
| تکرارها | بله | بله | بله (غیرفعال در عمل) | خیر |
| موجودی ماهانه، کیف پول، گردش حساب | بله | بله | خیر | خواندنی |
| چک‌ها، طلب‌ها، دنگ، طرف حساب‌ها، قالب پیامک | بله | بله | خیر | خیر |
| اقساط، صندوقچه (سه تب)، انتقال‌ها، دنگ گروهی (پنج تب)، دارایی ماهانه، تایم‌شیت (دو تب)، خودرو (شش تب)، مواعد شخصی | بله | خیر | خیر | خیر |
| یادآوری، یادآوری_ثبت، ناتیف، فعالیت | بله (برای هر کاربر) | خیر | خیر | خیر |
| ساختمان، واحدها، ساکنان | خیر | بله | خیر | خیر |

### ماتریس مجوزها (در سرور اجرا می‌شود)

ساختمان (از `memberRegistry.ts`):

| نقش | ثبت | صدور شارژ | صدور خودکار | اشخاص و واحدها | تنظیمات و اعضا |
| --- | --- | --- | --- | --- | --- |
| مدیر (manager) | بله | بله | بله | بله | بله |
| حسابدار (accountant) | بله | بله | خیر | بله | خیر |
| هیئت‌مدیره (board) | خیر | خیر | خیر | خیر | خیر |

خواندن همهٔ بخش‌ها برای همهٔ نقش‌هاست. هر عضو می‌تواند برای پنج کلید بازنویسی جداگانه داشته باشد.

حساب مشترک (از `sharedCan.ts`):

| نقش | ثبت | ویرایش دیگران | تسویه | بودجه و دسته‌ها | اعضا | خروجی |
| --- | --- | --- | --- | --- | --- | --- |
| صاحب (owner) | بله | بله | بله | بله | بله | بله |
| شریک (partner) | بله | خیر | بله | بله | خیر | بله |
| بیننده (viewer) | خیر | خیر | خیر | خیر | خیر | خیر |

قیدها: ساختمان همیشه حداقل یک مدیر دارد؛ حساب مشترک یک صاحب و حداکثر یک شریک دارد؛ هیچ‌کس نقش خودش را عوض نمی‌کند؛ هیچ‌کس به نقش صاحب دعوت نمی‌شود.

نظارت والدین:

- فرزند با رضایت صریح به والد اجازهٔ **خواندن** می‌دهد؛ فقط تب‌های ستون آخر جدول بالا.
- امروز این محدودیت فقط سمت کلاینت است و یک خوانندهٔ Drive کل فایل را می‌بیند. در سرور محدودیت در **لایهٔ API** اجرا می‌شود.
- قطع دسترسی را هر دو طرف باید بتوانند انجام دهند (تصمیم ۴ در بخش ۲۱).
- هر خواندن والد ثبت می‌شود و فرزند آن را می‌بیند.

### اجرا

- هر درخواست: هویت ← بارگذاری عضویت ← بررسی مجوز از رجیستری نقش‌ها (کد) ← اجرا.
- دفاع دوم: Row-Level Security در PostgreSQL روی `workspace_id` با `SET LOCAL app.user_id` در هر تراکنش، تا یک خطای کد به نشت میان کاربران نینجامد.
- داده‌های شخصی (قفل، کلیدهای push، یادآورها، خودرو، تایم‌شیت …) در فضای ساختمان و مشترک هرگز ساخته نمی‌شوند.

## ۷. هویت و ورود با OTP

### مدل

- هویت اصلی: شمارهٔ موبایل به شکل `+989xxxxxxxxx`. ورودی‌های `09…`، `9…` و ارقام فارسی و عربی نرمال می‌شوند (`normalizeDigits`). فقط موبایل ایران پذیرفته می‌شود.
- «ورود» و «ثبت‌نام» یک مسیر است. پاسخ‌ها وجود یا نبود حساب را لو نمی‌دهند.
- ایمیل دیگر هویت نیست. `legacy_email` فقط برای نگاشت داده‌های قدیمی است.

### مسیر ورود

```
POST /v1/auth/otp/request   { phone, deviceId, captcha? }
POST /v1/auth/otp/verify    { phone, code, challengeId, device:{ id, label, platform } }
 => { accessToken, refreshToken, expiresIn, user }
POST /v1/auth/refresh       { refreshToken }
POST /v1/auth/logout        { refreshToken, allDevices? }
GET  /v1/me
GET  /v1/me/sessions        DELETE /v1/me/sessions/:id
```

### قواعد OTP

| قاعده | مقدار پیشنهادی |
| --- | --- |
| طول کد | ۶ رقم |
| اعتبار | ۱۲۰ ثانیه |
| ذخیره | هش HMAC در Redis با کلید سرور؛ مقایسه با زمان ثابت |
| تلاش اشتباه | حداکثر ۵ بار؛ سپس کد باطل می‌شود |
| ارسال مجدد | حداقل ۶۰ ثانیه فاصله |
| سقف هر شماره | ۵ در ساعت و ۱۰ در روز |
| سقف هر IP | حدود ۲۰ در ساعت (قابل تنظیم) |
| سقف هر دستگاه | ۵ در ساعت |
| کپچا | پس از چند درخواست مشکوک؛ راه‌حل داخلی یا اثبات کار، نه سرویس خارجی |
| بودجهٔ پیامک | سقف روزانه و هشدار به مدیر |
| کد آزمایشی | فقط در محیط غیرتولید |
| لاگ | OTP و شمارهٔ کامل هرگز لاگ نمی‌شود |

### کنترل‌های تکمیلی

- **پر شدن خودکار کد:** در اندروید قالب پیامک طبق SMS Retriever (با هش اپ)؛ در وب فرمت WebOTP. به پشتیبانی قالب توسط درگاه پیامک بستگی دارد.
- **ارائه‌دهندهٔ پیامک پشت یک رابط:** `SmsProvider.send(template, phone, params)` با دو ارائه‌دهنده و failover (کاوه‌نگار، قاصدک، sms.ir، ملی‌پیامک از گزینه‌های رایج‌اند). روش «قالب تأییدشده» معمولاً سریع‌تر و ارزان‌تر از متن آزاد است. خط خدماتی و تأیید قالب زمان می‌برد.
- **شمارهٔ بازیافتی:** اپراتورها شمارهٔ قدیمی را به فرد دیگری می‌دهند. برای حساب بی‌فعالیتِ طولانی (مثلاً بیش از ۱۲ ماه) مرحلهٔ تأیید بیشتر در نظر بگیرید (تصمیم ۶).
- **تغییر شماره:** OTP روی شمارهٔ تازه و قدیم؛ در صورت ازدست‌رفتن شمارهٔ قدیم، مسیر پشتیبانی با ثبت در گزارش.
- **نشست:** توکن دسترسی ۱۵ دقیقه‌ای؛ توکن تمدید مات ۳۰ تا ۹۰ روزه، هش‌شده در DB، چرخشی و با **تشخیص استفادهٔ مجدد** (استفادهٔ دوباره از توکن چرخیده یعنی سرقت و کل زنجیره باطل می‌شود). هر نشست به یک دستگاه وصل است.
- **قرارداد پایداری:** خطای شبکه، timeout یا ۵xx هرگز کاربر را بیرون نمی‌اندازد؛ فقط ۴۰۱ «توکن تمدید نامعتبر» یعنی خروج. مهلت درخواست حداقل ۶۰ ثانیه است. رفتار فعلی `tokenRefresh.ts` و `offlineStart.ts` (backoff ۱۵، ۳۰، ۶۰ ثانیه و سپس ۵ دقیقه، شروع آفلاین با توکن منقضی) باید همان بماند.
- **ذخیرهٔ توکن:** در وب، توکن تمدید در کوکی HttpOnly و SameSite؛ در اندروید، حافظهٔ امن.
- **قفل اپ:** مستقل از سرور می‌ماند. «فراموشی PIN» با OTP جایگزین ورود Google می‌شود.
- **اتصال اختیاری Google:** فقط برای پشتیبان Drive (بخش ۹)، نه برای ورود.
- **بیومتریک وب:** `rp.id` برابر hostname است؛ تغییر دامنه آن را بی‌اعتبار می‌کند.

## ۸. همگام‌سازی آفلاین‌فرست

### قراردادهایی که باید بمانند

از بررسی `sheetSync*`، `syncOutbox*`، `outboxRebase` و `rowConflict*`:

1. نوشتن فوری در آینه و صف پایدار؛ نوشتن با بستن اپ گم نمی‌شود.
2. در صف، چند ویرایش یک ردیف ادغام می‌شوند و آخری می‌ماند. ترتیب هر ردیف حفظ می‌شود.
3. ایجاد و حذف idempotent هستند.
4. تعارض: وقتی ردیف از زمان خواندن عوض شده **و نویسندهٔ آخر دیگری است**، از کاربر پرسیده می‌شود («کدام بماند؟»). اگر نویسندهٔ آخر خود کاربر باشد (دستگاه دیگر)، بی‌صدا آخرین نوشته می‌ماند.
5. ادغام خودکار بدون پرسش: پرداخت‌های بدهی و طلب بر اساس شناسهٔ پرداخت؛ موجودی کیف پول با **دلتا** (`موجودی جدید = موجودی فعلی + (من - پایه)`).
6. خطای دائمی ← برگرداندن تغییر خوش‌بینانه و فهرست «نوشته‌های ناموفق»؛ خطای موقت ← backoff بدون از دست رفتن داده؛ ۴۲۹ جدی گرفته شود.
7. دریافت هرگز ردیفی را که تغییر محلیِ در صف دارد رونویسی نمی‌کند و ردیف حذف‌شدهٔ محلی را زنده نمی‌کند.
8. تشخیص ارزان تغییر (cursor) به‌علاوهٔ همگام‌سازی کامل روزانه؛ فوری هنگام بازگشت به اپ یا اتصال.
9. شروع آفلاین از حافظهٔ پنهان حتی با توکن منقضی.
10. وضعیت قابل نمایش: `idle|syncing|error`، شمار صف و ناموفق و تعارض، «آخرین دریافت» جدا از «آخرین ارسال».
11. یک ارسال‌کننده در هر لحظه، حتی بین چند تب.

### طرح

همگام‌سازی **عمومی** است و روی رجیستری تب‌ها (بخش ۵.۲) کار می‌کند؛ برای هر جدول کد جدا لازم نیست.

**شمارندهٔ ترتیب هر فضا.** هر تراکنش موفق `workspaces.seq` را با قفل ردیف افزایش می‌دهد و ردیف‌های تغییرکرده `last_seq` می‌گیرند. چون نوشتن‌ها در هر فضا پشت یک قفل سریال می‌شوند، «حفره»ای نیست که دریافت‌کننده تغییری را از دست بدهد. فضاها کوچک‌اند و این هزینه‌ای ندارد.

**دستهٔ اتمیک.** یک عمل کاربر (مثلاً «ثبت هزینه با اثر روی کیف پول») چند نوشتن است. کلاینت آن‌ها را در یک **تراکنش** با `id` یکتا (کلید idempotency) می‌فرستد و سرور همه یا هیچ را اعمال می‌کند. به این ترتیب بدون جابه‌جایی منطق دامنه به سرور، «نیمه‌کاره‌ماندن» که امروز در همه‌جا هست از بین می‌رود.

```
POST /v1/workspaces/{wid}/sync
{
  "deviceId": "...",
  "cursor": 18234,
  "txns": [
    { "id": "uuid-این-تراکنش",
      "ops": [
        { "op": "upsert", "table": "records", "key": "…", "baseVersion": 3, "data": { ... } },
        { "op": "wallet.move", "account": "…", "delta": -250000,
          "source": "ثبت", "recordId": "…", "applied": true },
        { "op": "delete", "table": "checks", "key": "…", "baseVersion": 2 }
      ] }
  ]
}
=> {
  "results": [ { "txnId": "…", "status": "applied|duplicate|rejected|conflict",
                 "conflicts": [ { "table": "…", "key": "…", "current": { ... } } ] } ],
  "changes": [ { "seq": 18235, "table": "…", "key": "…", "version": 4,
                 "deleted": false, "data": { ... } } ],
  "cursor": 18260,
  "hasMore": false
}
```

قواعد سرور:

- **وضعیت `duplicate`** وقتی همان `txn.id` قبلاً اعمال شده؛ پاسخ همان نتیجهٔ قبلی است.
- **نوشتن `upsert` با `baseVersion`:** اگر نسخه فرق دارد و `updated_by` کاربر دیگری است ← `conflict` با ردیف فعلی (رابط «کدام بماند؟» همان است). اگر `updated_by` خود کاربر است ← اعمال بی‌صدا. هر تعارض کل تراکنش را رد می‌کند.
- **دستور `wallet.move`:** `balance = balance + delta` در همان دستور SQL، و `balance_after` را سرور محاسبه می‌کند. **دستور `wallet.set`** برای نوشتن مطلق (مانده از پیامک، اصلاح دستی). عملیات صف آفلاین دلتا حمل می‌کند، نه موجودی جدید، و دقیقاً یک‌بار اعمال می‌شود.
- **پرداخت‌های JSON** با `mergePaymentsById` ادغام می‌شوند؛ ویرایش «مادر» هرگز پرداخت‌ها را رونویسی نمی‌کند.
- مجوز هر عملیات از رجیستری و ماتریس نقش‌ها بررسی می‌شود. تب‌های نامجاز برای نوع فضا رد می‌شوند.
- حدها: اندازهٔ بدنه، شمار عملیات در تراکنش (مثلاً ۲۰۰)، نرخ.

**دریافت:** `GET /v1/workspaces/{wid}/changes?since=<cursor>` تغییرها و قبرها را به ترتیب `seq` می‌دهد. کلاینتی که از افق قبر (مثلاً ۹۰ روز) عقب‌تر است `GET /v1/workspaces/{wid}/snapshot` می‌گیرد.

**اطلاع فوری:** `GET /v1/workspaces/{wid}/events` (SSE) فقط می‌گوید «چیزی تغییر کرد، seq=…». اگر SSE از شبکه عبور نکرد، همان polling ۳۰ ثانیه‌ای فعلی (فقط وقتی صفحه دیده می‌شود) کافی است.

**فیلتر محدوده:** برای والد و نقش‌های محدود، سرور `changes` را به تب‌های مجاز فیلتر می‌کند.

**چیزهایی که حذف می‌شوند چون فقط به Sheets مربوط بودند:** تب‌های سالانهٔ بایگانی و سقف ۵۰۰۰ ردیف، فشرده‌سازی شبکه، سقف ۵۰ هزار نویسه برای JSON، توکن‌های `accounting_rev`، تشخیص ویرایش دستی با `modifiedTime`، بازنویسی کل تب (`replace`) برای دسته‌ها. مفهوم «بستن سال» به‌عنوان قابلیت محصول می‌ماند (تطبیق، موجودی سال بعد، پشتیبان) ولی بایگانی فیزیکی نیست.

## ۹. پشتیبان‌گیری و بازیابی

این بخش دومین ستون معماری است. چون ساختار جدول‌ها همان ساختار تب‌هاست، **پشتیبان فعلی و بک‌اند یک قالب مشترک دارند.**

### ۹.۱ قالب پشتیبان (همان فعلی)

نام فایل `حساب کتاب · پشتیبان · <تاریخ شمسی و ساعت>.zip` است و با `fflate` ساخته می‌شود:

- فایل `manifest.json`: `{ "format": "hesab-ketab-backup", "formatVersion": 1, "appVersion", "spreadsheetLabel", "exportedAt", "tabs": [ { "name", "file", "rows" } ] }`
- یک `<نام تب>.csv` برای هر تب: UTF-8 با BOM، پایان خط CRLF، جداکنندهٔ کاما، نقل‌قول RFC-4180، ردیف اول عنوان‌های فارسی ستون‌ها.
- سلول‌هایی که با `= + - @` یا TAB/CR شروع می‌شوند و عدد نیستند، با `'` ابتدایی خروج می‌گیرند و هنگام خواندن برمی‌گردند (محافظ تزریق فرمول).
- شامل همهٔ تب‌های رجیستری (و تب‌های سالانه در فایل‌های قدیمی)، **به‌جز «قفل_اپ»**. فایل پیوست‌ها در zip نیست.

هر دو جهت از یک کد استفاده می‌کنند (بستهٔ مشترک): `packBackup(tabs)` و `unpackBackup(zip)`.

### ۹.۲ خروجی از بک‌اند

نقطهٔ `GET /v1/workspaces/{wid}/export` یک zip هم‌قالب می‌سازد: برای هر تب رجیستری، ستون‌ها را به ترتیب و عنوان فارسی بنویسد و مقدارها را با قالب خروجی بخش ۵.۳ چاپ کند. در خروجی:

- تب‌های `درآمد` و `هزینه` از جدول `records` با فیلتر نوع ساخته می‌شوند (همهٔ سال‌ها در یک تب).
- ستون «ثبت‌کننده» و ستون‌های ایمیلی با `legacy_email` یا برچسب متنی پر می‌شوند.
- ردیف‌های `نقش:` و `دعوت:` فقط برای اعضایی که `legacy_email` دارند بازسازی می‌شوند.
- فایل `manifest.json` همان قالب فعلی است. فیلدهای افزوده (مثلاً `source: "backend"`) برای خوانندهٔ قدیمی بی‌اثر باشند.

**نتیجه:** zip ساخته‌شده از بک‌اند را اپ نسخهٔ Google هم باز می‌کند. یعنی مهاجرت **برگشت‌پذیر** است.

### ۹.۳ بازیابی روی بک‌اند

نقطهٔ `POST /v1/workspaces/{wid}/import` ورودی را به یک شکل واحد می‌گیرد:

```
{ "mode": "merge" | "replace",
  "dryRun": true | false,
  "tabs": [ { "name": "چک‌ها", "headers": ["شناسه", ...], "rows": [["…", ...], ...] } ] }
```

این همان خروجی تجزیهٔ CSV است؛ یعنی **سه منبع یک مسیر دارند:**

| منبع | چگونه |
| --- | --- |
| فایل zip در دستگاه یا Drive | `unpackBackup` در کلاینت یا سرور، سپس همین بدنه |
| برگهٔ زندهٔ Google Sheets (کاربر هنوز در نسخهٔ Google است) | آینهٔ `string[][]` که کلاینت دارد به همین شکل می‌رود |
| پشتیبان بک‌اند دیگر یا نسخهٔ قبلی | همان zip |

الگوریتم (همان رفتار `runRestore` و `planTabRestore` فعلی):

1. **پیش‌نمایش** (`dryRun`): تب‌ها با رجیستری مطابقت داده می‌شوند. تب ناشناخته نادیده و گزارش می‌شود. `formatVersion` بزرگ‌تر از پشتیبانی‌شده رد می‌شود.
2. **تجزیه** هر ردیف با تجزیه‌گرهای مشترک (`normalizeSheetDate`، `parseNumeric`، `parseCreatedAtMs`، `remapLegacyRow` برای چیدمان‌های قدیمی)، با عنوان فارسی ستون‌ها و `aliases` رجیستری. ردیف کوتاه با مقدار خالی پر می‌شود. ردیف نامعتبر با شمارهٔ خط گزارش می‌شود، نه اینکه کل کار را بشکند.
3. **حالت «جایگزین»:** ردیف‌های تب با فایل عوض می‌شوند. **حالت «ادغام»:** ردیفی که کلیدش (`mergeKey` رجیستری) از قبل هست رد می‌شود؛ هرگز رونویسی نمی‌شود. کلید ادغام ستون اول است، به‌جز دسته‌بندی‌ها و یادآوری_ثبت (کل ردیف) و فعالیت (تک‌رکورد، موجود می‌ماند). تکراری درون فایل رد می‌شود؛ اولین شناسه برنده است.
4. **اتمیک بودن:** هر گروه وابسته در **یک تراکنش**: حساب‌های کیف پول با گردششان؛ بدهی/طلب/قسط با پرداخت‌هایشان؛ دنگ گروهی با پنج تبش. شکست یک گروه فقط همان گروه را برمی‌گرداند و گزارش پایانی می‌گوید چه چیزی وارد شد (قابل ادامه، idempotent با شناسه).
5. **اعتبارسنجی پس از واردکردن:** همان بررسی یکپارچگی فعلی (`integrityCheck`)؛ ناهمخوانی موجودی و مجموع گردش گزارش می‌شود و اصلاح یک‌ردیفی پیشنهاد می‌شود (بازیابی مستقل حساب‌ها و گردش می‌تواند ناهمخوان بسازد).
6. **ثبت:** هر واردکردن یک ردیف در `activity_log` می‌گیرد.

### ۹.۴ پشتیبان روی Drive

هدف: سیاست فعلی بماند و Drive فقط مقصد یک نسخهٔ zip باشد.

- **چه کسی می‌نویسد:** **کلاینت**، نه سرور. سرور در ایران به Drive دسترسی مطمئن ندارد و ذخیرهٔ توکن Google کاربر روی سرور هم لازم و مطلوب نیست.
- **جریان:** کلاینت توکن Google می‌گیرد (اتصال اختیاری «اتصال به Google برای پشتیبان»، بدون ارتباط با ورود)، `GET /export` را می‌خواند و zip را به پوشهٔ «پشتیبان» می‌نویسد. برچسب‌های فایل: `acctSpreadsheet=<شناسهٔ فضا>`، `acctBackup=auto|manual|update-*`، `acctVersion`.
- **سیاست‌های فعلی که می‌مانند:** پشتیبان هفتگی خودکار (اگر ۷ روز گذشته باشد)، نگه‌داری ۳ نسخهٔ خودکار (دستی هرگز پاک نمی‌شود)، پشتیبان پیش از به‌روزرسانی اپ، یادآوری پس از ۳۰ روز و هشدار پس از ۱۴ روز عدم پشتیبان (`backupReminder`، `autoBackupPlan`، `driveBackups`).
- **بازیابی:** کلاینت فهرست پوشه را می‌خواند، zip را می‌گیرد و به `POST /import` می‌دهد (پیش‌نمایش، سپس اعمال؛ دو حالت جایگزین و ادغام).
- **اگر Google در دسترس نبود** (فیلتر)، پشتیبان روی دستگاه (دانلود فایل) و پشتیبان سرور (بخش ۱۷) همچنان برقرارند. Drive یک لایهٔ بیشتر است، نه تنها پشتیبان.
- **پیوست‌ها** در zip نیستند. دو راه: (الف) zip گسترده با پوشهٔ فایل‌ها، برای گفتگوی بعدی؛ (ب) فقط در لحظهٔ مهاجرت اولیه، دانلود از Drive قدیمی و بارگذاری به فضای جدید (بخش ۱۳). تصمیم ۱۲.

### ۹.۵ هم‌قالب ماندن

- **آزمون رفت‌وبرگشت:** برای هر تب، `export(import(zip))` باید معادل `zip` باشد (جز نرمال‌سازی‌های آشکار: ارقام، قالب تاریخ). با zip واقعی چند نسخهٔ قدیمی اپ (شامل چیدمان‌های قدیمی) آزمون طلایی (golden) نگه‌داری شود.
- **نسخهٔ قالب:** `formatVersion` فقط با تغییر ناسازگار بالا می‌رود. افزودن ستون به انتهای تب مجاز است (همان قاعدهٔ فعلی «ستون تازه همیشه آخر»)؛ خوانندهٔ قدیمی ستون‌های اضافی را نادیده می‌گیرد.
- تغییر رجیستری (افزودن ستون و تب) = تغییر منبع واحد؛ DDL، خروجی، واردکردن و مجوز با هم عوض می‌شوند.

## ۱۰. قواعد دامنه سمت سرور

### تراکنش‌های واقعی (امروز هیچ‌کدام اتمیک نیست)

| جریان | آنچه در یک تراکنش رخ می‌دهد |
| --- | --- |
| ثبت، ویرایش یا حذف رکورد با حساب | رکورد + تغییر موجودی (دلتا) + ردیف گردش + همگام‌سازی پیوندها |
| انتقال بین حساب‌ها | ردیف انتقال + دو پا (موجودی و گردش). حذف: برگشت **همان چیزی که واقعاً حرکت کرده** و اگر یکی از حساب‌ها حذف شده، فقط ردیف انتقال برداشته می‌شود |
| پرداخت یا لغو پرداخت چک، قسط، طلب، بدهی | رکورد پیوندی + کیف پول + گردش + ردیف پرداخت + وضعیت مادر |
| وصل یک رکورد به چند بدهی یا طلب | یک ردیف پرداخت برای هر بدهی با همان `transaction_record_id`؛ جمع مبلغ‌ها دقیقاً برابر مبلغ رکورد؛ موجودی فقط یک بار (با خود رکورد) حرکت می‌کند. تا وقتی رکورد بیش از یک پیوند دارد ویرایش مبلغش رد می‌شود، برداشتن یک پرداختش رکورد را نگه می‌دارد و حذف یک بدهی رکوردهای مشترک را نگه می‌دارد |
| حذف رکورد | بازپرداخت موجودی (فقط اگر آخرین ردیف گردش آن رکورد «حذف» نیست) + حذف + بازکردن پرداخت‌های پیوندی |
| پرداخت شارژ واحد | درآمد + تخصیص به بدهی‌های واحد از قدیمی‌ترین + اعتبار اضافه |
| ثبت هزینهٔ ساختمان | رکورد + سهم واحدها + بدهی به پرداخت‌کنندهٔ غیر صندوق |
| سرویس خودرو | هزینه + ردیف سرویس + تاریخچه + کارکرد |
| آبشارهای دنگ گروهی | حذف گروه، قلم یا فرد با تخصیص‌ها |
| بازیابی پشتیبان | حساب‌ها و گردششان با هم (بخش ۹.۳) |

### قواعد مالی که عیناً حفظ می‌شوند

- **گردکردن:** `roundMoney` دو رقم، نیم به سمت دورتر از صفر. تقسیم دنگ: `floor` و باقی‌مانده به بزرگ‌ترین وزن. تقسیم هزینهٔ ساختمان: `floor` و باقی‌مانده به اولین واحد با وزن مثبت. شارژ بر پایهٔ متراژ یا نفرات: گرد به نزدیک‌ترین هزار؛ تخفیف خالی‌بودن با گرد ساده (حتی روی مبلغ اختصاصی واحد). تراز حساب مشترک: سهم پرداخت‌کننده در تقسیم مساوی `floor(مبلغ/۲)`.
- **شارژ ساختمان:** مبلغ اختصاصی واحد اگر غیرصفر باشد بر روش مقدم است؛ بدهکار = مستأجر وگرنه مالک؛ واحد بی‌بدهکار رد می‌شود؛ سررسید = روز ماه (حداکثر ۲۸) و اگر گذشته باشد «امروز». صدور خودکار فقط پس از اولین صدور دستی، فقط وقتی راه‌اندازی تمام شده و مالک موقت نیست، و جبران حداکثر ۱۲ ماه عقب‌افتادگی.
- **تخصیص پرداخت:** از قدیمی‌ترین بدهی (ترتیب: بدهی قبلی، سپس ماه‌های شارژ و سهم‌ها)، مازاد به اعتبار واحد.
- **سرویس خودرو:** کارکرد صعودی با مسیر اصلاح صریح؛ تأیید برای افت بیش از ۳۰٪؛ `nextKm = currentMileage + intervalKm`؛ هر چرخهٔ سرویس هزینه و تاریخچهٔ خودش را دارد.
- **صندوقچه:** میانگین موزون برای سود و زیان؛ فروش بیش از موجودی در سرور رد می‌شود.
- **چک:** مبلغ ثابت و پرداخت یک‌جا. **قسط:** سررسید با قاعدهٔ ۵ روزهٔ هم‌ماه و گیره‌کردن به طول ماه.
- **ردپا و بازگردانی:** فقط تا وقتی مقدار فعلی برابر «بعد» ثبت‌شده است؛ از مسیر ویرایش عادی (با همهٔ عوارض) و به‌صورت ردیف `revert` جدید.

## ۱۱. اعلان و زمان‌بند

### قاعدهٔ واحد

امروز سه پیاده‌سازی ناهماهنگ داریم: اسکریپت Google Apps Script، زمان‌بندی محلی اندروید و نمای داشبورد. سرور یک مجموعه قاعدهٔ واحد دارد.

انواع: قسط، چک، دنگ، مواعد شخصی، یادآور شبانه، یادآور روزانه، کارکرد خودرو، موعد خودرو، سرویس دوره‌ای خودرو. قاعده‌ها برای هر کاربر: فعال، روز قبل، ساعت، دقیقه.

- هر رویداد یک `ref` یکتا دارد؛ قید `UNIQUE(کاربر, ref, روز)` در `reminder_deliveries`.
- وضوح زمانی یک دقیقه، منطقهٔ `Asia/Tehran`.
- تحویل هر دستگاه ثبت می‌شود و اشتراک مرده با ۴۰۴ یا ۴۱۰ پاک می‌شود.

### کانال‌ها در ایران

اعلان Web Push مرورگرهای Chromium از `fcm.googleapis.com` عبور می‌کند که از داخل ایران پایدار نیست (باید مستقیم آزمایش شود).

| کانال | وضعیت |
| --- | --- |
| اعلان محلی اندروید | ادامه می‌یابد؛ آفلاین و بدون FCM. سرور قاعده و داده را همگام می‌کند و اعلان خودرو اضافه می‌شود |
| داخل اپ (SSE یا polling) | کانال اصلی هنگام باز بودن اپ |
| پیامک | رویدادهای مهم و به انتخاب کاربر (هزینه دارد) |
| اعلان Web Push (VAPID از سرور) | بهترین‌تلاش؛ برای Firefox و Safari کار می‌کند و برای FCM نامطمئن است |
| فرستندهٔ push داخلی | تصمیم باز؛ SDK بومی می‌خواهد |

| اشتراک تقویم (.ics) | امروز خروجی دستی است؛ می‌شود نشانی اشتراک |

اعلان‌های دیگر: مدیر ساختمان (بدهکاران، صدور نشدهٔ ماه، نتیجهٔ صدور خودکار، واریز برای تطبیق، سررسید چک، پیوستن عضو)؛ حساب مشترک («شریک رکورد را عوض کرد»)؛ و در آینده پیامک مستقیم به ساکنان (صورت‌حساب، یادآوری، رسید) که امروز مدیر دستی می‌فرستد.

قالب همهٔ پیام‌های ساخته‌شده در سرور با کلمهٔ فارسی شروع شود.

## ۱۲. پیامک بانکی

سیاست فعلی: **پیامک فقط یک کانال ورودی است.** تأیید آن از مسیر مشترک نوشتن رکورد می‌گذرد. API مخصوص پیامک ساخته نمی‌شود.

روی دستگاه می‌ماند: متن و فرستندهٔ پیامک، اسکن صندوق ورودی، تجزیه و تطبیق با الگو، حدس الگو، تشخیص جفت انتقال، موتور مانده، مسیریابی با شمارهٔ کارت.

به سرور می‌رود:

- **الگوها** (تب «قالب_پیامک»): متن ثابت بانک با شکاف‌های عددی؛ بدون مبلغ و کارت.
- **رکورد نهایی** با برچسب «ثبت از پیامک» و ستون سیستمی `origin_ref = HMAC(کلید کاربر، متن نرمال‌شدهٔ پیامک)` با ایندکس یکتا. این دو دستگاه با یک سیم‌کارت را از ساخت رکورد دوگانه بازمی‌دارد.
- حافظهٔ کم‌خطر برای هم‌رفتاری چند دستگاه (دستهٔ به‌خاطرسپرده برای فرستنده یا الگو، لنگر مانده) در `user_state`.

ثابت‌ها: واحد پیامک و فاکتور (ریال یا تومان) با ضریب ۱۰ به واحد برنامه تبدیل می‌شود؛ برای دلار و یورو تأیید ممکن نیست؛ سقف `10^12` تومان برای مبلغ و مانده؛ جفت انتقال: فاصلهٔ حداکثر ۱۰ دقیقه، مبلغ برابر، حساب‌های متفاوت.

ترتیب مانده: «مانده»ی تازه‌ترین پیامک موجودی را **مطلق** می‌گذارد (`wallet.set`)، وگرنه دلتا (`wallet.move`)؛ ترتیب بر اساس **زمان پیامک** است. رکورد با «اثر بر موجودی = خیر» وقتی مانده‌ای تازه‌تر آن را در برگرفته است.

شارژ ساختمان از پیامک: تطبیق با کارت و مبلغ (برابر کل بدهی یا ۱ تا ۶ برابر شارژ ماهانه). فقط اگر دقیقاً یک واحد بیاید، تأیید یک‌لمسی است؛ در بقیه انتخاب انسان لازم است. این منطق خالص روی دستگاه می‌ماند.

## ۱۳. فایل و پیوست

- امروز: تا ۳ پیوست برای هر رکورد، چک، طرح قسط و هزینهٔ خودرو. شناسه‌های Drive در ستون «پیوست». تصویر در مرورگر به حدود ۱۶۰۰ پیکسل و ۳۰۰ کیلوبایت JPEG فشرده می‌شود؛ PDF تا ۵ مگابایت.
- سرور: ستون «پیوست» همان‌طور می‌ماند، با شناسهٔ فایل سرور به‌جای شناسهٔ Drive. جدول `attachments(id, workspace_id, owner_table, owner_key, position, mime, size, storage_key, created_by)`. بارگذاری با نشانی امضاشدهٔ کوتاه‌مدت مستقیم به S3؛ خواندن هم امضاشده. سقف تعداد، نوع و حجم در سرور اجرا شود.
- صف آفلاین: بلوب‌ها در IndexedDB می‌مانند و **پس از** ردیف مربوط ارسال می‌شوند.
- پاک‌سازی فایل‌های یتیم با کار شبانه.
- **اسکن فاکتور (OCR):** کاملاً روی دستگاه اجرا می‌شود و به سرور چیزی اضافه نمی‌کند. خروجی آن همان ستون «اقلام» (JSON) و، اگر کاربر بخواهد، عکس فاکتور از مسیر عادی «پیوست» (`entryAttachmentSink`) است؛ مبلغ‌ها با همان تبدیل ریال به واحد برنامه (`toAppCurrency`) می‌آیند. سرور فقط باید فایل‌های ثابت مدل را برساند (بخش ۱۵). میان‌بر دوربین داشبورد فقط راه دیگری برای شروع همین اسکن است: عکس را در حافظهٔ برنامه تا فرم هزینه نگه می‌دارد، چیزی به سرور یا شیت نمی‌فرستد و چیدمان میان‌برها (شناسهٔ `scan-invoice`) فقط در حافظهٔ محلی همان دستگاه می‌ماند، نه در داده‌های حساب.
- فایل پیوست‌های Drive در پشتیبان نیستند (بخش ۹.۴).

## ۱۴. اشتراک و پرداخت

**اصل پیشنهادی:** داده‌ی کاربر گروگان نیست. خواندن، ورود و خروجی گرفتن همیشه آزاد است؛ فقط قابلیت‌های انتخاب‌شده قفل می‌شوند.

```sql
create table plans (id text primary key, title text, price numeric, period_days int, features jsonb);
create table subscriptions (id uuid primary key, user_id uuid, plan_id text,
  status text, started_at timestamptz, expires_at timestamptz, grace_until timestamptz);
create table payments (id uuid primary key, user_id uuid, subscription_id uuid, gateway text,
  authority text, amount numeric, status text, ref_id text, created_at timestamptz, paid_at timestamptz);
```

- **درگاه:** یکی از درگاه‌های داخلی (زرین‌پال، IDPay، نکست‌پی، زیبال و …). گردش: درخواست ← انتقال کاربر ← بازگشت ← **تأیید سمت سرور** (verify) ← فعال‌سازی. فقط پس از verify موفق اشتراک فعال می‌شود و ردیف پرداخت idempotent است. اینماد و تأیید ارائه‌دهنده زمان می‌برد.
- **مجوز قابلیت‌ها:** فهرست «قابلیت ← برنامهٔ لازم» در کد و یک middleware. کلاینت فقط نمایش می‌دهد.
- **سه مسیر همیشه آزاد:** ورود، خواندن داده، خروجی zip.

## ۱۵. میزبانی در ایران

اینترنت بین‌الملل از داخل ایران محدود و ناپایدار است. سرور نباید در مسیر هیچ درخواستی به سرویس خارجی وابسته باشد.

### وابستگی‌های فعلی که برداشته می‌شوند

| وابستگی فعلی | جایگزین |
| --- | --- |
| ورود Google و افزونهٔ ورود بومی اندروید | OTP پیامکی |
| ذخیرهٔ Google Sheets و Drive | PostgreSQL و فضای فایل داخلی |
| زمان‌بند Google Apps Script | worker بک‌اند |
| سرویس‌های Cloudflare Workers و KV | سرویس api و Redis |
| میزبانی GitHub Pages | CDN و میزبان داخلی |
| انتشار GitHub Releases برای APK و `version.json` | میزبان داخلی؛ قرارداد JSON همان می‌ماند |
| سرویس FCM برای Web Push | کانال‌های جایگزین (بخش ۱۱) |
| نقشهٔ OpenStreetMap و Nominatim | باید پایداری آن از ایران بررسی شود؛ جایگزین داخلی یا کش سرور |
| انتخابگر Google Picker | حذف |

نرخ ارز و طلا از `tgju.org` می‌آید که سایت ایرانی است و باید از سرور داخلی قابل دسترس باشد؛ پیش از اتکا آزمایش کنید.

### نکته‌های اجرایی

- **دامنه و گواهی:** دامنهٔ `.ir` از nic.ir. دسترسی ACME از سرور ایرانی را آزمایش کنید؛ در صورت مشکل از گواهی مدیریت‌شدهٔ CDN یا ارائه‌دهنده استفاده کنید.
- **ارائه‌دهنده:** گزینه‌های رایج: ابر آروان، لیارا، همراه‌وراه، ایران‌سرور، پارس‌پک، آسیاتک. قیمت، سیاست پشتیبان و پایداری را مستقیم بررسی کنید.
- **ساخت و انتشار:** `npm` و Docker Hub از ایران ممکن است مسدود یا کند باشند. تصویر Docker را بیرون از ایران در CI بسازید و در رجیستری داخلی بگذارید. سرور تولید نباید هنگام استقرار به اینترنت بین‌الملل نیاز داشته باشد.
- **ساخت پیوسته (CI):** GitHub Actions بیرون از ایران اجرا می‌شود؛ اتصال آن به سرور داخلی را آزمایش کنید و مسیر جایگزین بسازید.
- **محیط‌ها:** `api.<دامنه>` برای تولید و `api-dev.<دامنه>` برای آزمایشی، با پایگاه داده‌های جدا. اپ آزمایشی روی زیردامنهٔ جدا می‌رود، نه زیر `/dev/` همین origin؛ پیشوند `dev:` برای storageها بی‌نیاز می‌شود.
- **فایل‌های ثابت سنگین:** مدل‌های خواندن فاکتور (`public/ocr/v1/` و فایل wasm در `assets/`، حدود ۲۷ مگابایت) باید از CDN داخلی با سرآیند کش بلندمدت (`immutable`) برسند. برنامه آن‌ها را فقط هنگام اولین اسکن می‌گیرد و با `CacheFirst` در Service Worker (کش `invoice-ocr-models`) نگه می‌دارد تا بعد آفلاین کار کند؛ مسیرهای `ocr/v<نسخه>/` و `ort-wasm*.wasm` باید پایدار بمانند. APK هم همین فایل‌ها را از `public/**` می‌گیرد.
- **قانون و مقررات:** الزام ذخیره‌سازی داخل کشور، اینماد برای درگاه پرداخت و قوانین خط پیامک را از منبع رسمی راستی‌آزمایی کنید. این سند حقوقی نیست.

### چیدمان استقرار اولیه

```
سرور ۱ (برنامه):  caddy ، api ، worker ، redis
سرور ۲ (داده):    postgres (با WAL archiving) ، پشتیبان‌گیری
فضای S3 داخلی:   فایل کاربران، پشتیبان رمزشدهٔ DB
CDN داخلی:        فایل‌های ثابت اپ ، version.json ، APK
```

در شروع یک سرور هم کافی است. DB را طوری بسازید که جابه‌جایی به سرور جدا فقط عوض‌کردن نشانی اتصال باشد.

## ۱۶. امنیت و حریم خصوصی

### کنترل‌های سرور

- رمزنگاری TLS اجباری، HSTS، سرآیندهای امنیتی، CORS محدود به origin اپ، `https://localhost` برای Capacitor و `http://localhost:5173` برای توسعه.
- نرخ‌دهی چندلایه (IP، کاربر، شماره، مسیر) در Redis.
- همهٔ ورودی‌ها با Zod؛ اندازهٔ بدنه محدود؛ پرسش‌ها پارامتری.
- مجوز در هر نقطهٔ پایانی (بخش ۶) و RLS به‌عنوان لایهٔ دوم.
- نویسنده و زمان را سرور می‌زند (`created_by`, `updated_by`)؛ ستون «ثبت‌کننده» برچسب نمایشی است، نه مرجع هویت (امروز کلاینت می‌نویسد و قابل جعل است).
- توکن‌های تمدید هش‌شده؛ کلیدهای JWT چرخشی؛ رازها در محیط یا مدیر راز.
- لاگ بدون اطلاعات شخصی؛ شمارهٔ موبایل ماسک‌شده؛ بدون OTP.
- رمزنگاری دیسک و پشتیبان‌ها.
- واردکردن و خروجی zip فقط برای عضو مجاز (`export` در حساب مشترک)، با محدودیت اندازه و نرخ.

### قفل اپ

قفل اپ (PIN با PBKDF2 با ۶۰۰ هزار تکرار، کلید AES-GCM، بیومتریک) مستقل از سرور می‌ماند و فقط آینهٔ IndexedDB را رمز می‌کند. صف ارسال و نشست امروز رمز نیستند و باید پوشش داده شوند.

### حریم خصوصی

- صفحهٔ `public/privacy.html` امروز می‌گوید «سرور و پایگاه دادهٔ خودمان نداریم، داده فقط در Drive شماست». باید بازنویسی شود: مسئول داده، محل نگهداری در ایران، مدت نگهداری، حذف حساب، پیامک و ارائه‌دهنده‌اش، درگاه پرداخت، پشتیبان اختیاری Drive.
- حقوق کاربر: خروجی کامل (zip) و حذف حساب با مهلت.
- نظارت والدین: شفافیت برای فرزند.

## ۱۷. مشاهده‌پذیری و پشتیبان سرور

- **سنجه‌ها:** نرخ و تأخیر درخواست، خطا، طول صف، نرخ موفقیت پیامک (مهم‌ترین شاخص سلامت ورود)، تأخیر همگام‌سازی، شمار تعارض. Prometheus و Grafana، یا Uptime Kuma.
- **خطا:** سرویس‌های ابری خارجی ممکن است از ایران در دسترس نباشند؛ نسخهٔ خودمیزبان (GlitchTip) را در نظر بگیرید.
- **هشدار:** قطع ارائه‌دهندهٔ پیامک (با سوئیچ خودکار به دومی)، پر شدن دیسک، تأخیر WAL، شکست verify پرداخت.
- **پشتیبان PostgreSQL:** `pg_dump` شبانه و بایگانی WAL (pgBackRest یا WAL-G) برای بازیابی تا نقطه‌ای مشخص؛ نسخهٔ رمزشده در فضای ارائه‌دهندهٔ دوم (در ایران) و یک نسخهٔ آفلاین. **بازیابی را هر ماه آزمایش کنید.**
- **پشتیبان zip زمان‌بندی‌شده:** هفتگی برای هر فضا (همان قالب بخش ۹)، با نگهداری ۳ نسخه. این لایهٔ جدا از پشتیبان Drive است و همیشه روی سرور وجود دارد.
- **ظرفیت:** در شروع یک سرور کافی است. داده هر کاربر کوچک است و گلوگاه اول معمولاً پیامک است، نه DB.

## ۱۸. فهرست API

## ۱۹. ساختار ریپوی سرور

```
server/
  src/
    modules/
      auth/  workspaces/  sync/  backup/  ledger/  building/  shared/
      reminders/  sms/  billing/  files/  admin/
    platform/
      db/  redis/  queue/  sms-provider/  storage/  push/  config/  logger/
    jobs/                (صدور شارژ، نرخ‌ها، یادآور، پشتیبان، پاک‌سازی)
  migrations/            (ساخته‌شده از رجیستری + دستی برای قیدها)
  test/
packages/
  shared/                (رجیستری تب‌ها، طرح Zod، تجزیه‌گرها و قالب‌دهنده‌ها،
                          packBackup/unpackBackup، تاریخ شمسی، پول، نرمال‌سازی،
                          منطق خالص دامنه؛ هم کلاینت و هم سرور)
```

- ماژول `backup` مسئول خروجی و واردکردن است؛ ماژول `sync` فقط رجیستری را می‌خواند.
- هر ماژول لایه‌های `routes` ← `service` ← `repo` دارد و فقط از طریق service با ماژول دیگر حرف می‌زند.
- محل پوشه‌ها قابل جابه‌جایی است. این سند به این وابسته نیست که سرور در همین مخزن باشد یا جدا؛ فقط `packages/shared` از هر دو طرف باید قابل وارد کردن باشد.
- سقف ۳۰۰ خط برای هر فایل و قاعدهٔ «پیش از ساخت، جستجو» برای سرور هم برقرار بماند.

## ۲۳. اشکال‌های کشف‌شده

رفتارهای فعلی که بررسی نشان داد. چون سرور همان قواعد را اجرا می‌کند، هرکدام یا آگاهانه همان‌طور می‌ماند، یا در سرور درست می‌شود؛ در هر حال باید ثبت شوند:

- قید «جمع پرداخت‌های یک رکورد ≤ مبلغ رکورد» را شیت نمی‌تواند بین تب‌ها تضمین کند؛ دو دستگاه می‌توانند هم‌زمان بیش از مبلغ رکورد تقسیم کنند. جدول پرداخت در سرور نباید روی `record_id` یکتا باشد و این قید را باید خود سرور بررسی کند.
- بررسی «این رکورد جای دیگری هم پرداخت است؟» فقط از نسخهٔ محلی شیت می‌خواند؛ اگر دستگاه دیگر هم‌اکنون سهمی افزوده باشد و همگام نشده باشد، حذف پرداخت یا بدهی رکورد را پاک می‌کند و پرداخت دیگر تا بازبینی بعدی به رکورد نبوده اشاره می‌کند. سرور باید این بررسی را خودش انجام دهد.
- قفل مبلغ رکورد هم برای رکوردی است که چند بدهی را پوشش می‌دهد و هم برای رکوردی که پس از برداشتن بقیهٔ سهم‌ها فقط بخشی از مبلغش پرداخت یک بدهی مانده است.
- رکوردی که چند پرداخت از چند بدهی دارد، در نسخهٔ قدیمی‌تر اپ با ویرایش مبلغ، همهٔ پرداخت‌ها را با مبلغ کامل بازنویسی می‌کند؛ نسخهٔ تازه جلوی ویرایش مبلغ را می‌گیرد.

- واردکردن CSV خودرو ستون «کارکرد_اجباری» را می‌اندازد (فقط ۱۱ ستون می‌خواند). رجیستری این را حل می‌کند.
- ساعت یادآور ۰ همیشه ۹ می‌شود.
- هشدار موعد خودرو فقط در روز دقیق ارسال می‌شود.
- سرویس دوره‌ای هر روز دوباره ارسال می‌شود.
- اشتراک push مرده هرگز پاک نمی‌شود.
- ستون `createdAt` رشتهٔ محلی فارسی است؛ در یک جا تاریخ سرویس از `createdAt.split(',')[0]` درمی‌آید.
- «زمان پرداخت» چک ترکیبی از ISO و رشتهٔ فارسی است.
- ستون `dueDay` ساختمان در توضیح «روز پس از صدور» و در کد «روز ماه» (۱ تا ۲۸) است.
- بازنویسی مجوز `record` برای عضو هیئت‌مدیره فقط رابط را باز می‌کند و Drive فقط‌خواندنی می‌ماند.
- پرداخت بدون `keepCredit` مازاد را بی‌سروصدا دور می‌ریزد.
- پس از صدور هم‌زمان، تکراریِ **پرداخت‌شده** حذف نمی‌شود (بدهکار دوباره).
- فهرست مجاز والد فقط سمت کلاینت اعمال می‌شود.
- دو مسیر برگشت کارکرد خودرو از منبع‌های متفاوت استفاده می‌کنند.
- حذف حساب کیف پول شناسهٔ آویزان در رکورد، گردش، انتقال، هدف و تکرار می‌گذارد.
- حذف یا تغییر نام طرف حساب به رکوردها و چک‌ها و بدهی‌ها نمی‌رسد؛ تغییر نام دسته تکرارها، پین الگوها و قواعد پیامک را به‌روز نمی‌کند.
- عکس ماهانهٔ دارایی خالص فقط وقتی نوشته می‌شود که کاربر اپ را در ماه تازه باز کند.
- شمارندهٔ ارجاع در KV غیر اتمیک است.
- شمارش تلاش PIN در localStorage است و با پاک‌کردن آن دور زده می‌شود؛ توکن نشست در localStorage ساده نگه‌داشته می‌شود.

## پیوست الف: رجیستری تب‌ها

راهنمای نوع‌ها: `id` شناسه، `text` متن، `int` عدد صحیح، `num` عدد، `money` پول، `qty` مقدار، `date` تاریخ، `ts` زمان، `dt` زمان بدون منطقه، `bool` بله/خیر، `json` ساختار، `enum` فهرست ثابت. «خالی=» یعنی معنی سلول خالی. هر خط: `عنوان فارسی ستون = کلید:نوع`، به ترتیب ستون‌ها. نوع‌ها بر اساس نام ستون و `types/` فعلی پیشنهاد شده‌اند و هنگام نوشتن رجیستری با کد `*Row.ts` هر ماژول تأیید می‌شوند.

اتصال به نوع فضا: «هر» یعنی شخصی، ساختمان و مشترک (جز مواردی که گفته شده)؛ «ش» فقط شخصی؛ «ش+س» شخصی و ساختمان؛ «س» فقط ساختمان.
